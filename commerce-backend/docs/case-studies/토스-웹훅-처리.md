# 토스 웹훅 처리 — 상태별 전략 패턴

가상계좌 결제는 PG의 동기 응답만으로 완결되지 않습니다. 사용자의 실제 입금까지 시간 차가 발생하고, 입금 완료는 토스가 **웹훅으로 비동기 통보**하기 때문입니다. 입금 대기·취소·만료·중단 역시 동일한 웹훅 엔드포인트로 서로 다른 상태값과 함께 들어옵니다.

---

## 1. 인터페이스로 경계 분리

### 증상

웹훅을 단일 컨트롤러에서 if-else로 분기하면 상태가 추가될 때마다 컨트롤러가 비대해지고, 기존 흐름을 수정해야 하므로 **OCP(개방-폐쇄 원칙) 위배**입니다. 결제 수단을 전략 패턴으로 분리한 것과 동일한 발상으로, 웹훅도 **상태별 전략**으로 분리했습니다.

### After — `TossWebHookStatusStrategy`

```java
public interface TossWebHookStatusStrategy {
    boolean supports(PaymentStatus paymentStatus);
    void updateTossStatus(DataPayment dataPayment);
}
```

각 구현체는 자신이 담당하는 `PaymentStatus`만 지원합니다.

- **DoneStrategy** — 가상계좌 입금 완료. `payment.confirm()` 호출 + 동일 주문의 `OrderItem`을 `PAYMENT_COMPLETED`로 전이.
- **WaitingForDepositStrategy** — 가상계좌 발급 후 입금 대기. `payment.waitForDeposit()` 호출(`READY` → `WAITING_FOR_DEPOSIT`).
- **CanceledStrategy** — 결제 취소. `payment.cancel()` + `OrderItem` `PAYMENT_CANCELED_CONFIRM`.
- **AbortedStrategy** — 결제 중단. `payment.abort()` + `OrderItem` `ABORTED`.
- **ExpiredStrategy** — 가상계좌 만료. `payment.expire()`.

신규 상태(예: `PARTIAL_CANCELED`)가 추가돼도 **새 전략 구현체를 추가하는 방식으로** 후처리 책임을 분리할 수 있고, 컨텍스트와 컨트롤러의 구조는 유지됩니다.

## 2. 컨텍스트가 디스패치를 담당

`TossWebHookContext`가 들어온 상태에 맞는 전략을 골라 실행합니다.

```java
@Component
@RequiredArgsConstructor
@Transactional
public class TossWebHookContext {

    private final List<TossWebHookStatusStrategy> tossWebHookStatusStrategyList;
    private final PaymentRepository paymentRepository;

    public void execute(DataTossWebHook dataTossWebHook) {
        Payment payment = paymentRepository.findByPaymentNo(dataTossWebHook.paymentKey())
                .orElseThrow(() -> new ApiNotFoundException("결제 정보를 찾을 수 없습니다."));

        DataPayment dataPayment = new DataPayment(
                payment.getPaymentNo(),
                payment.getOrderId(),
                payment.getPaymentMethod(),
                dataTossWebHook.status(),
                payment.getTotalAmount()
        );

        TossWebHookStatusStrategy strategy = tossWebHookStatusStrategyList.stream()
                .filter(s -> s.supports(dataTossWebHook.status()))
                .findFirst()
                .orElseThrow(() -> new ApiBadRequestException("지원하지 않는 웹훅 상태입니다."));

        strategy.updateTossStatus(dataPayment);
    }
}
```

이 예제의 웹훅 DTO(`DataTossWebHook`)는 상태 전이 설명에 필요한 필드만 단순화해 받고, 컨텍스트가 내부 도메인 표현(`DataPayment`)으로 변환해 전략에 전달합니다. **전략 구현체는 외부 PG 페이로드 전체 형식에 의존하지 않습니다.**

## 3. 재시도 / 중복 호출 — 도메인 멱등성으로 대응

### 증상

웹훅은 응답 실패 시 다시 들어올 수 있습니다. 토스페이먼츠는 200 응답을 받지 못하면 최대 7회까지 재전송하므로, 우리 쪽에서 같은 상태 전이를 다시 처리해도 안전해야 합니다.

### 두 가지 선택지

1. **인프라 차원에서 차단** — Filter 또는 별도 테이블로 `(paymentKey, status)` UNIQUE 제약을 두어 2차 호출 차단
2. **도메인 메서드 자체를 멱등하게 설계**

### After — 도메인 멱등성 채택

후자를 골랐습니다. **멱등성을 도메인의 책임으로 끌어올리면**, 웹훅뿐 아니라 어떤 경로로 같은 상태 전이가 시도되어도 결과가 일관되며, 별도 인프라(테이블·캐시) 없이도 안전합니다.

```java
public void confirm() {
    if (paymentStatus == PaymentStatus.DONE) {
        return;                                    // 멱등
    }
    if (paymentStatus != PaymentStatus.READY
            && paymentStatus != PaymentStatus.IN_PROGRESS
            && paymentStatus != PaymentStatus.WAITING_FOR_DEPOSIT) {
        throw new IllegalStateException("결제 확정은 READY/IN_PROGRESS/WAITING_FOR_DEPOSIT 상태에서만 가능합니다.");
    }
    this.paymentStatus = PaymentStatus.DONE;
    this.paidAt = LocalDateTime.now();
}
```

`waitForDeposit()`, `cancel()`, `abort()`, `expire()`도 동일한 패턴으로 구현했습니다. 이미 동일 상태인 경우 즉시 `return`하므로, **같은 상태 전이가 다시 들어와도 결과가 바뀌지 않습니다.**

## 4. Filter / Controller

`TossWebHookFilter`(`OncePerRequestFilter` 상속)는 `/v1/payment/toss/webhook/` 경로 요청을 필터링해 Content-Type을 검증하고 수신 로그를 기록합니다. 운영 환경에서는 토스 IP 화이트리스트 검증도 같이 들어가야 하지만, 본 레포지토리에서는 해당 부분을 단순화했습니다.

```java
@RestController
@RequestMapping("/v1/payment/toss/webhook")
@RequiredArgsConstructor
public class RestControllerToss {

    private final TossWebHookContext tossWebHookContext;

    @PostMapping("/payment-status-changed")
    public ResponseEntity<ReturnResult<Void>> handleStatusChanged(@Valid @RequestBody DataTossWebHook dataTossWebHook) {
        tossWebHookContext.execute(dataTossWebHook);
        return Response.ok();
    }
}
```

엔드포인트는 `POST /v1/payment/toss/webhook/payment-status-changed`로, 토스 콘솔에 등록한 URL이 그대로 라우팅됩니다.

---

## 확인 포인트

- `DONE` / `WAITING_FOR_DEPOSIT` / `CANCELED` / `ABORTED` / `EXPIRED` 상태를 각각 독립 전략으로 분리했습니다.
- 컨텍스트는 `supports(...)`만 보고 전략을 고르므로 상태별 후처리 분기가 한곳에 몰리지 않습니다.
- 도메인 메서드는 같은 상태 전이가 다시 들어와도 결과를 유지하도록 작성했습니다.

---

## 정리

결제 수단 전략과 동일한 **"Context + 전략 리스트 주입 + supports 디스패치"** 구조로 웹훅 처리를 일원화했습니다. 신규 상태 추가 시 전략 클래스 한 개를 추가하는 것으로 작업이 종결되며, 컨텍스트와 컨트롤러는 수정하지 않습니다. 또한 **도메인 메서드에 멱등성을 내장**해, 별도 인프라(중복 체크 테이블·캐시) 없이 토스의 재시도 정책에 안전하게 대응합니다.
