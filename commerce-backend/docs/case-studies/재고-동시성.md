# 재고 감소 동시성 처리

여러 사용자가 동일 상품을 동시에 결제하는 상황에서 재고 정합성을 보장하는 것이 목표였습니다. **재고가 한 번 음수로 떨어지면 보상해야 할 데이터가 광범위하게 발생**하기 때문에, 사후 정정이 아닌 사전 차단이 필요했습니다.

---

## 1. 문제 상황 — Lost Update

한 variant의 재고가 **5개** 남은 상태에서 두 결제 요청이 거의 동시에 들어오는 경우를 가정해 봅시다. 두 요청이 모두 "재고 5개"를 읽은 후 각자 차감을 시도하면, 나중에 저장하는 트랜잭션이 앞선 저장값을 덮어쓰는 **lost update**가 발생합니다.

| 시점 | 결제 1 | 결제 2 | 실제 DB 재고 |
|------|--------|--------|------------|
| 1 | 재고 조회: 5 | | 5 |
| 2 | | 재고 조회: 5 | 5 |
| 3 | 5 - 3 = 2 저장 | | 2 |
| 4 | | 5 - 3 = 2 저장 | 2 |

결제는 양쪽 모두 성공으로 처리되지만 실제 판매 수량은 **6개**이며, 재고 6개가 차감돼야 할 자리에 3개만 차감된 상태로 남습니다. 결제는 완료됐는데 배송이 불가능한 상황으로 직결됩니다.

---

## 2. 1차 시도 — `synchronized`

초기에는 `synchronized` 키워드만으로 해결될 줄 알았습니다. 그러나 두 가지 한계에 부딪혔습니다.

### 한계 1 — 프록시 트랜잭션의 락 해제 / 커밋 시점 차이

`@Transactional` 메서드는 Spring AOP 프록시를 거쳐 호출됩니다. `synchronized` 블록이 끝나서 락이 풀린 시점과 트랜잭션이 실제로 **커밋되는 시점 사이에 간격**이 존재합니다. 그 짧은 윈도우 안에 다른 스레드가 들어오면 커밋되지 않은 데이터를 읽게 됩니다.

### 한계 2 — 다중 인스턴스 환경

JVM 프로세스 단위의 락이므로, **서버를 2대 이상 띄우면 각 JVM이 자기 락만 들고 있어** 인스턴스 간 동시 진입을 차단할 수 없습니다.

---

## 3. 2차 시도 — DB 비관적 락

다중 인스턴스 환경에서도 DB는 단일하므로, 락 계층을 DB로 이관했습니다. JPA의 `@Lock(LockModeType.PESSIMISTIC_WRITE)`와 IN절을 조합해, **필요한 모든 variant를 단일 쿼리로 락킹**합니다.

```java
public interface ProductVariantRepository extends JpaRepository<ProductVariant, UUID> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("select pv from ProductVariant pv where pv.id in :variantIdList")
    List<ProductVariant> findAllByIdInForUpdate(@Param("variantIdList") List<UUID> variantIdList);
}
```

### 데드락 가능성 낮추기 — IN절 일괄 락킹

설계 시 데드락도 함께 고려했습니다. variant마다 락을 개별로 요청하면, 트랜잭션 1이 A를, 트랜잭션 2가 B를 선점한 채 서로 상대의 락을 기다리는 **교차 대기**가 발생할 수 있습니다.

IN절로 필요한 키를 한 번에 요청하면 개별 요청보다 락 획득 흐름을 단순하게 유지할 수 있습니다. 여기에 동일한 접근 순서를 지키는 방식까지 결합하면, 서로 다른 순서로 여러 row를 잡을 때보다 데드락 가능성을 낮출 수 있습니다.

## 4. 차감은 결제 트랜잭션 내부에서만

재고 차감은 결제 트랜잭션 진입 시점에만 발생합니다. **주문 생성 시점에는 재고를 건드리지 않습니다.** `PaymentService.startPayment(...)`가 결제 트랜잭션을 개시할 때 `OrderItemFinder`로 해당 주문의 모든 OrderItem을 수집한 후, `StockService.decrementStocks(...)`로 한 번에 락을 잡고 차감합니다.

어느 하나의 item이라도 재고가 부족하면 결제 전체를 실패 처리(`ApiConflictException`)하며, **동일 트랜잭션이므로 차감이 함께 롤백**되어 일부만 차감된 중간 상태가 발생하지 않습니다.

```java
@Service
@RequiredArgsConstructor
@Transactional
public class PaymentService {

    private final PaymentContext paymentContext;
    private final OrderRepository orderRepository;
    private final OrderItemFinder orderItemFinder;
    private final StockService stockService;

    public Payment startPayment(DataPaymentRequest request) {
        Order order = orderRepository.findByOrderNumber(request.orderNumber())
                .orElseThrow(() -> new ApiNotFoundException("주문을 찾을 수 없습니다."));

        List<OrderItem> orderItemList = orderItemFinder.findAllByOrderId(order.getId());
        if (!stockService.decrementStocks(orderItemList)) {
            throw new ApiConflictException("재고가 부족하여 결제를 시작할 수 없습니다.");
        }

        Payment payment = paymentContext.executePayment(toDataPayment(order, request));
        order.updateOrderStatusForConfirm();
        return payment;
    }
}
```

차감 로직 자체는 도메인이 책임집니다. **DB 락이 동시성을 보장**하므로 도메인 메서드는 단순한 비즈니스 규칙 검증으로 유지됩니다.

```java
public boolean decrementStock(int quantity) {
    if (stock < quantity) {
        return false;
    }
    stock = stock - quantity;
    return true;
}
```

---

## 확인 포인트

- 재고 차감은 결제 트랜잭션 안에서만 발생합니다.
- 여러 item 중 하나라도 차감에 실패하면 `ApiConflictException`으로 결제 전체가 롤백됩니다.
- 비관적 락으로 같은 variant를 동시에 차감하는 흐름을 직렬화합니다.

---

## 정리

처음에는 `synchronized` 한 줄로 끝낼 수 있을 줄 알았으나, **프록시 트랜잭션의 시점 차이**와 **다중 인스턴스 환경**이라는 두 한계에 부딪히면서 DB 락으로 전환했습니다. IN절 기반 일괄 락킹으로 동시성 제어를 단순화했고, 차감 시점을 결제 트랜잭션 내부로 한정함으로써 결제 실패 시의 보상 처리 부담을 제거했습니다.
