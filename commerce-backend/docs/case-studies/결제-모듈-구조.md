# 확장 가능한 결제 모듈 구조

기존 구조는 단일 판매자, 단일 결제 수단을 전제로 설계되어 있어 다중 판매자 상품을 한 주문에 묶거나 결제 수단을 추가하는 작업이 어려웠습니다. 다중 판매자와 결제 수단 확장을 처음부터 전제로 두고 다시 설계했습니다.

---

## 1. 주문/결제 도메인 — 5계층 분리

결제와 주문 도메인을 다섯 계층으로 분리했습니다.

```
Payment → Order → OrderVendor → OrderProduct → OrderItem
```

- **Payment** — 결제 수단·금액·상태. 이 예제에서는 주문 1건당 하나의 결제 흐름을 전제로 둡니다.
- **Order** — 주문 합계와 구매자 정보, 주문 상태(`PENDING_CONFIRM` → `CONFIRM`).
- **OrderVendor** — 판매자별 묶음 + 배송비.
- **OrderProduct** — 상품 단위 + 주문 시점 이름 스냅샷. **원본 상품 정보가 나중에 변경돼도 주문 내역은 시점 그대로 보존**됩니다.
- **OrderItem** — variant 단위 옵션·수량·단가·할인. `OrderItemStatus`로 결제 이후 상태를 **item 단위**로 관리합니다.

### 엔티티 참조 — ID + 인덱스, FK·객체 그래프 매핑 없음

엔티티 간 참조는 ID 컬럼만 두고 인덱스로 조회 성능을 챙겼습니다. JPA `@OneToMany`/`@ManyToOne` 객체 그래프 매핑이나 DB FK 제약은 두지 않았습니다.

```java
@Entity
@Table(name = "order_vendor", indexes = {
    @Index(name = "idx_order_vendor_order_id", columnList = "orderId")
})
public class OrderVendor {
    @Id @GeneratedValue
    private UUID id;
    private UUID orderId;          // Order 참조 (FK 없음, 인덱스만)
    private UUID vendorId;
    private String vendorName;
    private long deliveryFee;
}
```

이유는 두 가지입니다.

- **마이그레이션·서비스 분리 유연성** — 향후 주문/결제 도메인을 별도 서비스로 분리하거나 DB를 분리할 때 FK 제약이 발목을 잡지 않게 하기 위함입니다.
- **N+1 / LAZY 함정 차단** — 객체 그래프 자동 탐색을 막고, **명시적 리포지터리 호출을 강제**해서 의도하지 않은 조회를 사전에 차단합니다.

## 2. 주문 생성 — 5계층을 한 트랜잭션에

`OrderCreateService`가 `CreateOrderRequest`를 받아 5계층을 동일 트랜잭션 안에서 한 번에 생성합니다. **주문 생성 시점에는 재고를 차감하지 않습니다.** 결제 승인 시점에 차감하는 것이 자연스럽고, 결제 실패 시 보상 처리(재고 복원)의 부담도 사라집니다.

```java
@Service
@RequiredArgsConstructor
@Transactional
public class OrderCreateService {

    private final OrderRepository orderRepository;
    private final OrderVendorRepository orderVendorRepository;
    private final OrderProductRepository orderProductRepository;
    private final OrderItemRepository orderItemRepository;

    public Order createOrder(CreateOrderRequest request) {
        if (orderRepository.findByOrderNumber(request.orderNumber()).isPresent()) {
            throw new ApiConflictException("이미 존재하는 주문번호입니다.");
        }
        Order order = orderRepository.save(Order.create(...));
        // OrderVendor → OrderProduct → OrderItem 순차 생성
        return order;
    }
}
```

## 3. 결제 수단 — 전략 패턴으로 분리

### 증상

결제 수단마다 후처리가 다른데(카드는 즉시 승인, 가상계좌는 발급 후 대기), 이를 단일 클래스의 if-else로 분기하면 새 수단을 추가할 때마다 기존 코드를 건드려야 합니다. **OCP(개방-폐쇄 원칙) 위배**.

### After — 인터페이스로 경계 분리

```java
public interface PaymentStrategy {
    boolean supports(PaymentMethod paymentMethod);
    void processPayment(DataPayment dataPayment, UUID paymentId);
}
```

현재 두 개의 구현체가 존재합니다.

- **CardPaymentStrategy** — 카드 결제. 즉시 승인 흐름.
- **VirtualAccountPaymentStrategy** — 가상계좌. 발급만 수행하고 이후 처리는 웹훅에 위임.

`PaymentContext`는 Spring이 자동 주입한 `List<PaymentStrategy>` 중 `supports(method)`가 true인 전략을 선택해 실행합니다.

```java
@Component
@RequiredArgsConstructor
@Transactional
public class PaymentContext {

    private final List<PaymentStrategy> paymentStrategyList;
    private final PaymentRepository paymentRepository;

    public Payment executePayment(DataPayment dataPayment) {
        Payment saved = paymentRepository.save(Payment.create(...));
        PaymentStrategy strategy = paymentStrategyList.stream()
                .filter(s -> s.supports(dataPayment.paymentMethod()))
                .findFirst()
                .orElseThrow(() -> new ApiBadRequestException("지원하지 않는 결제 수단입니다."));
        strategy.processPayment(dataPayment, saved.getId());
        return saved;
    }
}
```

신규 결제 수단 추가 시 `PaymentMethod` 확장과 전략 구현체 추가가 필요하지만, **컨텍스트와 호출 흐름은 수정하지 않아도 됩니다.**

## 4. 결제 시작 — 재고 차감과 결제 처리의 단일 트랜잭션

`PaymentService.startPayment(...)`가 결제 트랜잭션의 단일 진입점입니다. 처리 순서는 다음과 같습니다.

1. 주문 조회
2. OrderItem 수집 후 **비관적 락**으로 재고 차감
3. `PaymentContext.executePayment`로 전략 디스패치
4. `Order.updateOrderStatusForConfirm()` 호출 (`PENDING_CONFIRM` → `CONFIRM`)

어느 단계에서 예외가 발생하더라도 **동일 트랜잭션이 일괄 롤백**되므로, 결제·재고·주문 상태가 흐름 도중에 어긋날 수 없습니다.

상세한 재고 동시성 처리 흐름은 [재고-동시성.md](재고-동시성.md)에서, 가상계좌의 비동기 입금 완료 통보 처리는 [토스-웹훅-처리.md](토스-웹훅-처리.md)에서 다룹니다.

## 5. 동기 / 비동기 결제 흐름이 같은 인터페이스 아래로

카드 결제는 PG 응답이 동기로 반환되므로, `CardPaymentStrategy`가 호출 직후 `payment.confirm()`을 통해 `DONE` 상태로 전이시키고, 동일 주문의 `OrderItem`을 `PAYMENT_COMPLETED`로 일괄 전이합니다.

가상계좌는 이 예제에서 발급 이후 처리를 웹훅 쪽으로 넘기기 위해 결제 시작 직후 `READY` 상태로 남겨 둡니다. 이후 `WAITING_FOR_DEPOSIT` / `DONE` 상태 전이는 웹훅 전략이 담당합니다. **두 흐름이 동일한 `PaymentStrategy` 인터페이스 아래에서 자연스럽게 통합**됩니다.

---

## 확인 포인트

- **CARD** — `CardPaymentStrategy`가 선택되면 `Payment`는 `DONE`, `Order`는 `CONFIRM`, `OrderItem`은 `PAYMENT_COMPLETED`로 전이됩니다.
- **VIRTUAL_ACCOUNT** — `VirtualAccountPaymentStrategy`는 결제 시작 시 후처리를 비워 두고, 이후 상태 전이를 웹훅 전략에 맡깁니다.
- 결제 시작 흐름 안에서 재고 차감과 주문 상태 전이가 같은 트랜잭션으로 묶입니다.

---

## 정리

확장 지점이 **결제 수단 인터페이스 한 곳으로 집중**되었고, 주문 구조가 결제 → 판매자 → 상품 → 옵션 단위까지 코드에 명시적으로 드러납니다. 신규 결제 수단 추가나 판매자 단위 요구사항 변경 시 수정 범위가 명확하게 제한됩니다.
